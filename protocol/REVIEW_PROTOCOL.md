# Evidence-Mining and Review Protocol

## 1. Purpose

Build a review that is useful for algorithm researchers rather than another catalogue of optimization metaphors.

The review separates four kinds of statements:

- **documented fact** — directly supported by a source;
- **reported empirical result** — true only for the reported experimental conditions;
- **cross-study inference** — synthesized from multiple studies and explicitly marked as synthesis;
- **project finding** — generated by this repository's own experiments.

No project finding is presented as a literature finding and no literature claim is upgraded beyond its evidence.

## 2. Review questions

### RQ1 — Coverage
Which optimization algorithm families and representative algorithms have been studied, when, and for which problem classes?

### RQ2 — Mechanisms
What computational mechanisms actually distinguish the algorithms?

### RQ3 — Evidence
For each algorithm, what has been established about solution quality, convergence, robustness, scalability, cost, and reliability?

### RQ4 — Benchmark adequacy
Which problem characteristics are represented or missing in existing evaluations?

### RQ5 — Structural overlap
Which nominally different algorithms are mechanistically close or potentially redundant?

### RQ6 — Failure regimes
Under what observable conditions does performance deteriorate, become unstable, or reverse relative to competitors?

### RQ7 — Reproducibility
Can the published algorithm and its principal empirical claims be reproduced from available descriptions/code/data?

### RQ8 — Research gaps
Which unknowns are genuine evidence gaps rather than generic future-work statements?

### RQ9 — Gap repair
Which gaps can be addressed by better experimental design, parameter adaptation, a transferable mechanism, theory, or a genuinely new optimizer?

## 3. Search strategy

Search across major scholarly indexes and publisher databases using combinations of:

- optimization / optimiser / optimizer;
- global optimization;
- black-box optimization;
- metaheuristic;
- evolutionary algorithm;
- swarm;
- derivative-free;
- Bayesian optimization;
- multiobjective / many-objective;
- constrained;
- noisy / robust / stochastic;
- dynamic;
- large-scale;
- mixed-integer / mixed-variable;
- benchmarking;
- structural bias;
- reproducibility;
- algorithm comparison;
- performance profile;
- sensitivity;
- ablation;
- parameter control.

Maintain a search log containing database, query, date, filters, and returned/retained counts.

## 4. Study inclusion

A source may enter the evidence base when it contributes at least one of:

- original algorithm;
- substantial algorithmic mechanism;
- theoretical result;
- benchmark methodology;
- systematic or critical review;
- comparative experiment;
- reproducibility evidence;
- structural-bias evidence;
- benchmark-suite design;
- real-world evaluation;
- negative or contradictory result.

## 5. Study exclusion

Exclude or isolate sources that:

- provide no inspectable algorithmic definition;
- duplicate an earlier method without substantive evidence;
- compare under manifestly incomparable budgets without correction;
- report only selected best runs;
- lack enough methodological detail to interpret the experiment;
- make broad superiority claims from a narrow benchmark;
- cannot be linked to a verifiable bibliographic record.

Exclusion is recorded, not silently discarded.

## 6. Per-algorithm audit

For each algorithm record:

### Identity
- canonical name;
- aliases;
- year;
- original source;
- family;
- source code if available.

### Mechanism
- representation;
- initialization;
- update operator;
- information sources;
- neighborhood/topology;
- selection/replacement;
- memory;
- adaptation;
- constraint handling;
- restart/diversity mechanism;
- stopping condition.

### Theory
- convergence results;
- assumptions;
- invariance properties;
- complexity;
- known guarantees and counterexamples.

### Empirical evidence
- benchmark suites;
- dimensions;
- budgets;
- number of runs;
- competitors;
- parameter policy;
- statistical tests;
- metrics;
- real-world problems.

### Reliability
- source implementation available?;
- independently reproduced?;
- pseudocode/code agreement?;
- parameter ambiguity?;
- stochastic seed disclosure?;
- compute/budget disclosure?

### Known limitations
- structural bias;
- premature convergence;
- scaling;
- noise sensitivity;
- constraint sensitivity;
- initialization sensitivity;
- parameter sensitivity;
- computational/memory cost.

### Unknowns
Every untested or unresolved condition becomes an explicit evidence-gap candidate.

## 7. Mechanism-first representation

Each algorithm is encoded as a structured mechanism vector instead of an inspiration label.

Suggested fields:

```text
representation
population_structure
initialization
variation_operator
direction_information
selection
replacement
memory
elitism
adaptation
restart
constraint_handling
surrogate_use
gradient_use
second_order_information
parallelism
termination
```

This representation enables clustering and structural-distance analysis.

## 8. Benchmark audit

Do not treat benchmark suites as neutral by default.

Annotate each problem or suite by:

- modality;
- separability;
- conditioning;
- rotation/non-separability;
- ruggedness;
- deception;
- constraints;
- noise;
- dynamic behavior;
- mixed variables;
- dimensional scalability;
- evaluation cost;
- known optimum;
- real-world provenance.

We will distinguish **benchmark coverage** from **algorithm performance**.

## 9. Comparison protocol

Comparisons must use equivalent information and computational budgets wherever meaningful.

For stochastic algorithms:
- multiple independent seeds;
- identical problem instances;
- identical evaluation budgets;
- predeclared stopping rules;
- raw-run retention.

Competitors should cover:
1. classical/reference baseline;
2. mechanistically closest algorithm;
3. established strong algorithm;
4. recent relevant algorithm;
5. target-regime specialist where appropriate.

Avoid selecting competitors after seeing results.

## 10. Metrics

Use metrics appropriate to the problem class, potentially including:

- best/median/mean error;
- success probability;
- expected/runtime-to-target;
- empirical cumulative distribution;
- performance/data profiles;
- convergence trajectories;
- variance and tail risk;
- constraint violations;
- hypervolume/IGD+ for multiobjective settings;
- wall-clock time;
- objective evaluations;
- memory;
- algorithm overhead;
- sensitivity measures.

Final-value ranks alone are insufficient.

## 11. Failure-frontier analysis

For an algorithm A and condition vector θ, define a declared success criterion before testing.

Map the transition between conditions under which the criterion is and is not satisfied.

Potential axes:
- dimension;
- budget;
- conditioning;
- non-separability;
- noise;
- constraint density;
- dynamics;
- initialization;
- hyperparameters.

These transitions are treated as capability boundaries, not merely ranking changes.

## 12. Gap classification

Every gap receives one primary type:

- THEORY
- MECHANISM
- STRUCTURAL_BIAS
- BENCHMARK
- SCALABILITY
- ROBUSTNESS
- CONSTRAINT
- DYNAMIC
- MIXED_VARIABLE
- REPRODUCIBILITY
- COMPARISON
- REAL_WORLD
- STATISTICAL
- COMPUTATIONAL_COST

Each gap must state:
- what is known;
- what is missing;
- why it matters;
- strongest supporting sources;
- testable hypothesis;
- minimal resolving experiment;
- appropriate baselines;
- artifact expected.

## 13. Novel algorithm rule

A new algorithm is **not** a predetermined project deliverable.

It is justified only if the gap analysis identifies a failure that cannot be adequately addressed by:
- better tuning;
- an existing mechanism;
- a simple restart;
- changed constraint handling;
- budget normalization;
- an established hybrid;
- an existing adaptive variant.

Prefer a transferable mechanism over a metaphor-based optimizer.

If a new method is proposed:
1. state the gap first;
2. derive the mechanism from that gap;
3. identify the closest prior mechanisms;
4. provide ablation;
5. compare parent vs parent+mechanism;
6. equalize budgets;
7. test outside the regime used to motivate it;
8. report failures as well as wins.

## 14. Evidence freeze before writing

The review paper begins only after:
- registry is stable;
- source ledger is audited;
- algorithm cards are complete for the declared scope;
- benchmark matrix is generated;
- all planned experiments have passed validation;
- raw results are archived;
- statistical analyses are frozen;
- figures/tables regenerate from raw data;
- gap registry is finalized.

This prevents the narrative from driving the evidence.
